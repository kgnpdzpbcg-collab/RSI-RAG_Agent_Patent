# V0.5 算法核心：面向航空电子知识证据状态的递归自优化检索增强智能体

> 状态：**算法核心冻结版（用于后续查新、Feature Chart 和专利 V0.5 正文）**  
> 目标：将“航空电子领域”从应用标签推进到算法本体，使领域知识结构、适用性约束、证据状态和递归检索策略形成不可分割的技术链。  
> 说明：本版本不再以“Agentic RAG + Memory”作为主要创新表述，而以“航空电子证据状态迁移驱动的递归检索优化”作为核心。

---

# 1. 核心技术问题

当前通用 RAG / Agentic RAG 在航空电子装备知识服务中存在三个关键问题：

1. **不知道当前任务究竟需要哪些工程证据。**  
   通用 RAG 主要以语义相关性判断检索结果，但航空电子维修/测试任务通常要求同时满足设备型号、模块、版本、工况、测试位置、测试步骤、合格判据、维修动作等工程约束。

2. **相关文档不等于可用证据。**  
   高相似度文档可能属于其他设备型号、旧版本手册、不同功能模块或不同测试工况。如果不进行 Effectivity / Applicability 校验，就可能把“相关但不适用”的知识误作为有效证据。

3. **Agent 每次仍可能从零探索。**  
   即使当前任务能够通过多轮检索补齐证据，普通 Agentic RAG 通常不会稳定学习“在某种航空电子证据状态下，采取什么知识获取动作最有效”。因此相似任务会重复无效检索，且历史成功/失败经验难以直接改变未来动作先验。

本方案的核心思想为：

\[
\boxed{
\text{航空电子证据需求建模}
\rightarrow
\text{适用性约束证据形成}
\rightarrow
\text{证据状态与缺口识别}
\rightarrow
\text{缺口驱动领域检索动作}
\rightarrow
\text{验证状态迁移}
\rightarrow
\text{历史状态迁移经验递归更新动作策略}
}
\]

---

# 2. 总体算法框架

完整流程如下：

\`\`\`text
用户航空电子知识任务 q
        ↓
任务解析与对象识别
        ↓
AERT：航空电子证据需求模板 Rq
        ↓
构造初始 Evidence State Σ0
        ↓
执行初始领域检索
        ↓
候选文本 → KEO 知识证据对象
        ↓
Equipment / Module / Revision / Condition / Validity 适用性门控
        ↓
更新 Evidence State Σt
        ↓
识别 Missing / Uncertain / Conflict Gap
        ↓
根据当前 Context + Evidence State / Gap 选择领域 Retrieval Action At
        ↓
执行检索动作
        ↓
获得新 KEO 并验证
        ↓
Σt  --At-->  Σt+1
        ↓
是否满足任务结束条件？
   ┌────┴────┐
   │         │
  否         是
   │         ↓
继续检索   生成可追溯答案
   │         ↓
   └──── 记录 Verified State Transition
             ↓
       构造 GAEU
             ↓
       聚合同类状态迁移经验
             ↓
      更新 Gap/State-Action Policy
             ↓
      未来相似状态优先调用
\`\`\`

本方案的 RSI 不定义为“Agent 自动修改自身所有能力”，而严格限定为：

> **根据经验证的航空电子证据状态迁移经验，递归调整未来相似证据状态下的检索动作先验。**

# 3. 数据结构一：AERT 航空电子证据需求模板

AERT：**Avionics Evidence Requirement Template**。

其作用不是存储知识，而是将一个航空电子知识任务转换成“需要哪些工程证据才能认为该任务得到充分回答”。

定义：

\[
R_q=
\langle
C_q,\mathcal{E}_q,\mathcal{M}_q,\Theta_q,\mathcal{D}_q
\rangle
\]

其中：

- \(C_q\)：任务上下文；
- \(\mathcal{E}_q\)：证据槽位集合；
- \(\mathcal{M}_q\)：强制证据槽位集合；
- \(\Theta_q\)：各证据槽位满足条件；
- \(\mathcal{D}_q\)：证据依赖关系。

## 3.1 任务上下文 \(C_q\)

建议包含：

\`\`\`text
equipment_model       装备/型号
board_or_module       板卡/功能模块/通道/接口
task_type             任务类型
operating_condition   供电/负载/飞行阶段/测试模式等工况
maintenance_state     维护、测试或故障隔离状态
hardware_revision     硬件版本
software_revision     软件版本（若相关）
document_baseline     当前有效技术资料版本基线
\`\`\`

字段未知时允许标记为 \`UNKNOWN\`。未知不是简单缺省，而可被转化为后续的 applicability gap。

## 3.2 不同任务类型对应不同证据模板

### （1）故障原因分析

\[
\mathcal E_q^{fault}=
\{
e_{sym},
e_{event},
e_{principle},
e_{mechanism},
e_{test},
e_{criterion},
e_{action}
\}
\]

- \(e_{sym}\)：故障现象 / 异常表现；
- \(e_{event}\)：BIT/BITE、故障码、告警、复位等关联事件；
- \(e_{principle}\)：相关模块工作原理；
- \(e_{mechanism}\)：候选故障机理 / 可能原因；
- \(e_{test}\)：区分性测试位置与步骤；
- \(e_{criterion}\)：正常范围、阈值、合格判据；
- \(e_{action}\)：后续检查或维修动作。

### （2）测试规程查询

\[
\mathcal E_q^{test}=
\{
e_{precondition},
e_{location},
e_{instrument},
e_{procedure},
e_{criterion},
e_{safety}
\}
\]

分别对应前置条件、测试点/位置、测试设备、操作步骤、判断标准和安全限制。

### （3）BIT/BITE故障码解释

\[
\mathcal E_q^{BIT}=
\{
e_{code},
e_{meaning},
e_{trigger},
e_{applicability},
e_{cause},
e_{check},
e_{limitation}
\}
\]

### （4）参数查询

至少包括：

\[
\{
e_{object},
e_{parameter},
e_{value},
e_{unit},
e_{condition},
e_{source}
\}
\]

### （5）维修处置查询

至少包括：

\[
\{
e_{fault\_condition},
e_{maintenance\_action},
e_{precondition},
e_{procedure},
e_{postcheck},
e_{escalation}
\}
\]

# 4. AERT 中的证据依赖关系

AERT 不应只是并列的 slot list，而应包含工程先决依赖。

用有向依赖关系表示：

\[
e_i \prec e_j
\]

表示在 \(e_i\) 未满足前，\(e_j\) 即使检索到相关内容，也不能直接被认定为最终有效证据。

典型关系例如：

\[
Effectivity
\prec
TestProcedure
\]

表示未确认设备/模块/版本适用性时，测试规程只能作为候选证据，不能标记为 SATISFIED。

又如：

\[
TestLocation
\land
TestCondition
\prec
AcceptanceCriterion
\]

表示只有明确测试位置和测试条件后，某个数值范围才能作为当前任务的合格判据。

故障分析任务可表示为：

\[
Effectivity
\prec
Symptom/FaultCode
\prec
Principle
\prec
DiscriminativeTest
\prec
Criterion
\prec
Action
\prec
PostVerification
\]

该依赖并非要求所有任务严格线性执行，而用于约束“证据什么时候可以被确认有效”。

# 5. 数据结构二：KEO 知识证据对象

KEO：**Knowledge Evidence Object**。

普通 RAG 的 chunk 只是文本相似性单元；KEO 是经过领域化结构封装、可进入证据状态机的工程证据对象。

定义：

\[
K_i=
\langle
Content_i,
Type_i,
App_i,
Prov_i,
Claim_i
\rangle
\]

建议结构：

\`\`\`text
KEO
├─ content
│  └─ 原始证据文本/表格/条目
├─ evidence_type
│  └─ principle / mechanism / BIT /
│     test / criterion / action / case ...
├─ applicability
│  ├─ equipment
│  ├─ module
│  ├─ hardware_revision
│  ├─ software_revision
│  ├─ operating_condition
│  └─ validity
├─ provenance
│  ├─ document_name
│  ├─ document_type
│  ├─ chapter/page/item
│  ├─ revision
│  ├─ effective_date
│  └─ supersession
└─ claim
   ├─ supported_slot
   └─ supported_statement
\`\`\`

KEO 仍然基于文本 + metadata，不要求构建知识图谱。

---

# 6. 航空电子知识适用性门控

相关性不能替代适用性。

对每个 KEO 定义关键适用条件：

\[
App=
\{
equipment,
module,
revision,
condition,
validity
\}
\]

每个维度：

\[
a_k(K_i,q)\in\{0,u,1\}
\]

其中：

- \(0\)：明确冲突 / 不适用；
- \(u\)：未知或尚未确认；
- \(1\)：确认适用。

定义适用性状态：

\[
H(K_i,q)=
\begin{cases}
0,& \exists k,\ a_k=0\\
u,& \nexists k:a_k=0\ \land\ \exists k:a_k=u\\
1,& \forall k,\ a_k=1
\end{cases}
\]

解释：

- \(H=0\)：禁止作为最终证据；
- \(H=u\)：可用于探索，但不能单独把强制槽位置为 SATISFIED；
- \(H=1\)：允许作为有效证据参与槽位更新。

因此系统执行的是：

\[
\text{先 Effectivity / Applicability Gate，再 Evidence Ranking}
\]

而不是“高相似度即高可信证据”。

---

# 7. Evidence State：航空电子证据状态机

对于当前 AERT 中每个槽位：

\[
state(e_j)\in
\{
EMPTY,
PARTIAL,
SATISFIED,
CONFLICT
\}
\]

含义：

- **EMPTY**：尚无候选证据；
- **PARTIAL**：已有相关内容，但缺字段、适用性未知、依赖前提未满足或证据不完整；
- **SATISFIED**：有完整、适用、来源可追溯且满足依赖关系的证据；
- **CONFLICT**：存在两个或多个当前适用的证据对象给出不一致结论，且尚未完成冲突消解。

整个任务在第 \(t\) 轮的证据状态为：

\[
\Sigma_t=
[
state(e_1),
state(e_2),
\ldots,
state(e_m)
]
\]

这比普通“已检索 evidence set”更强，因为它明确表示当前工程证据是否可用。

---

# 8. 证据覆盖与任务结束条件

可为辅助排序定义：

\[
c_j=
\begin{cases}
0,&EMPTY\\
0.5,&PARTIAL\\
1,&SATISFIED\\
0,&CONFLICT
\end{cases}
\]

总覆盖度：

\[
C_t=
\frac{\sum_{j=1}^{m}w_jc_j}
{\sum_{j=1}^{m}w_j}
\]

但任务不能只依赖总分结束。

设强制槽位集合为 \(\mathcal M_q\)，则结束需要同时满足：

\[
C_t\ge\tau_C
\]

\[
\forall e_j\in\mathcal M_q,\quad state(e_j)=SATISFIED
\]

以及：

\[
N_{conflict}=0
\]

如存在强制槽位 PARTIAL / EMPTY / CONFLICT，则必须继续检索、适用性核验或冲突消解。

---

# 9. Evidence Gap 的三类划分

根据 \(\Sigma_t\) 定义：

\[
G_t=
G_t^{miss}
\cup
G_t^{uncertain}
\cup
G_t^{conflict}
\]

其中：

\[
G_t^{miss}=\{e_j|state(e_j)=EMPTY\}
\]

\[
G_t^{uncertain}=\{e_j|state(e_j)=PARTIAL\}
\]

\[
G_t^{conflict}=\{e_j|state(e_j)=CONFLICT\}
\]

这三类 Gap 采用不同检索/核验动作：

- Missing：重点是获取缺失知识；
- Uncertain：重点是补全字段、确认型号/版本/工况或依赖前提；
- Conflict：重点是查找当前有效的上位资料、技术通告或版本链，进行冲突消解。

---

# 10. 缺口感知的证据排序

对通过适用性门控的 KEO，可计算：

\[
Score(K_i|q,G_t)
=
H(K_i,q)
\left[
\lambda_1S_{sem}
+\lambda_2S_{lex}
+\lambda_3S_{source}
+\lambda_4S_{gap}
\right]
\]

其中：

- \(S_{sem}\)：语义相关性；
- \(S_{lex}\)：关键词/专业术语匹配；
- \(S_{source}\)：来源权威性及文档类型优先级；
- \(S_{gap}\)：对当前证据缺口的补齐价值。

定义：

\[
S_{gap}(K_i,G_t)
=
\sum_{e_j\in G_t}
w_j\cdot cover(K_i,e_j)
\]

因此，一篇重复解释已满足“故障机理”的高相似文本可能低于一篇能补齐“测试点和判据”的中等相似度测试规程。

# 11. 领域化 Retrieval Action 空间

Agent 不直接在完全开放的 Tool 空间中自由选择，而根据 Gap 类型从领域动作空间中选择。

定义：

\[
\mathcal A=
\{
A_{source},
A_{filter},
A_{query},
A_{file},
A_{page},
A_{context},
A_{version},
A_{conflict}
\}
\]

典型映射：

| 当前 Evidence Gap | 领域动作 |
|---|---|
| 缺工作原理 | 原理/设计资料限定检索 + 模块功能术语扩展 |
| 缺 BIT/BITE 代码含义 | 故障代码表限定检索 + 当前设备/软件版本过滤 |
| 缺测试位置 | 测试规程或维修手册限定检索 |
| 缺测试步骤 | 指定规程定位 + page / adjacent-page context |
| 缺正常范围/合格判据 | 参数表、测试规程表格及上下文检索 |
| 缺设备适用性 | 型号/构型/适用范围查询 |
| 缺版本适用性 | revision / effective-date / supersession 核验 |
| 缺历史处置经验 | 同型号 + 同工况历史维修案例检索 |
| 缺维修动作 | 维修手册 / 故障隔离程序限定检索 |
| 证据冲突 | 最新有效手册 / 技术通告 / 上位规程 / 版本链核验 |

具体动作对象：

\[
A_t=
\langle
target,
source,
filter,
query,
tool,
context
\rangle
\]

例如：

\`\`\`text
target_gap:
    acceptance_criterion

source:
    test_procedure

filter:
    equipment = current_model
    module = 5V_output
    revision = effective_revision

query:
    "5V output test point normal range"

tool:
    search_by_file

context:
    current_page + adjacent_pages
\`\`\`

# 12. 核心经验对象：GAEU / Verified State Transition

为了避免 GAEU 仅退化成一般的“Action + Evidence Gain”，其本质应定义为：

> **经过验证的航空电子证据状态迁移记录。**

GAEU 可保留命名：

**Gap-Action Experience Unit**

但数学结构优先采用：

\[
X_t=
\langle
C_t,
\Sigma_t,
G_t,
A_t,
\Sigma_{t+1},
V_t,
Cost_t,
Prov_t
\rangle
\]

其中：

- \(C_t\)：航空电子任务上下文；
- \(\Sigma_t\)：动作前证据状态；
- \(G_t\)：动作前证据缺口；
- \(A_t\)：实际领域检索动作；
- \(\Sigma_{t+1}\)：动作后的证据状态；
- \(V_t\)：新增证据的适用性、来源和支撑验证；
- \(Cost_t\)：工具调用、Token、上下文、轮次等代价；
- \(Prov_t\)：知识库版本、文档版本、策略版本。

因此真正学习的是：

\[
\boxed{
\Sigma_t
\xrightarrow{A_t}
\Sigma_{t+1}
}
\]

而不是简单学习“动作新增了几条证据”。

# 13. State Transition 的收益评价

证据覆盖增益：

\[
\Delta C_t=C_{t+1}-C_t
\]

强制槽位增益：

\[
\Delta M_t=
\sum_{e_j\in\mathcal M_q}
\mathbf{1}
[
state_t(e_j)\neq SATISFIED
\land
state_{t+1}(e_j)=SATISFIED
]
\]

综合动作效用：

\[
U_t=
\alpha\Delta C_t
+\beta\Delta M_t
+\gamma V_t
-\delta Cost_t
-\mu Conflict_t
\]

其中：

- \(V_t\)：新增证据是否通过设备、模块、版本、工况和来源验证；
- \(Conflict_t\)：是否引入新的未解决冲突；
- \(Cost_t\)：检索资源消耗。

如果一个动作召回很多相似文本，但没有使任何关键槽位发生有效状态转移，则其长期价值不应很高。

# 14. RSI 的策略对象：State/Gap-Action Policy

定义当前决策状态：

\[
Z_t=(C_t,\Sigma_t,G_t)
\]

长期学习策略：

\[
\pi(A|Z)
\]

即：

> 在特定航空电子任务上下文和证据状态下，何种领域知识获取动作历史效果最好。

历史动作价值可以表示为：

\[
Q(A|Z)=
\frac{
\sum_i sim(Z,Z_i)\rho_iU_i
}{
\sum_i sim(Z,Z_i)\rho_i+\epsilon
}
\]

其中：

- \(sim(Z,Z_i)\)：当前状态与历史状态的相似程度；
- \(\rho_i\)：历史经验验证可靠度；
- \(U_i\)：历史动作的状态迁移效用。

动作选择：

\[
A_t^*=
\arg\max_{A\in\mathcal A(G_t)}
[
Q(A|Z_t)-\kappa Cost(A)
]
\]

若不存在足够可靠的历史经验：

> 回退到 Base Agent Planner。

因此 RSI 只提供动作先验，不替代当前 Planner 的适应能力。

---

# 15. 策略递归更新

后续相似任务再次产生经验证的状态迁移时，可递推更新：

\[
Q_{t+1}(A|Z)
=
(1-\eta\rho_t)Q_t(A|Z)
+\eta\rho_t U_t
\]

当动作稳定补齐关键证据：

\[
Q\uparrow
\]

当动作无效：

\[
Q\downarrow
\]

当动作使用错误版本、引入冲突或导致不适用证据进入回答：

\[
Q\downarrow\downarrow
\]

因此形成：

\[
P_t
\rightarrow
P_{t+1}
\rightarrow
P_{t+2}
\]

即“经验证状态迁移 → 更新未来动作先验”的递归自优化。

# 16. 版本和 Effectivity 进入 Policy Scope

长期策略必须包含：

\`\`\`text
Policy Scope
├─ equipment_family
├─ board_or_module
├─ task_type
├─ knowledge_type
├─ operating_condition
├─ hardware/software revision range
└─ document_baseline
\`\`\`

例如维修手册：

\`\`\`text
Rev.C → Rev.D
\`\`\`

系统不能简单把旧策略覆盖掉，而可以形成：

\`\`\`text
P17:
  scope: manual <= Rev.C

P24:
  scope: manual >= Rev.D
\`\`\`

若当前 revision 未知，则产生：

\[
G^{uncertain}_{revision}
\]

优先执行版本适用性核验，而不是直接采用历史检索路径。

用户任务：

# 18. V0.5 相对 V0.4 的关键变化

V0.4 的核心是：

\[
Trajectory
\rightarrow REU
\rightarrow Policy
\]

V0.5 改为：

\[
\boxed{
AERT
\rightarrow
Effectivity-aware\ KEO
\rightarrow
Evidence\ State
\rightarrow
Gap-conditioned\ Action
\rightarrow
Verified\ State\ Transition
\rightarrow
Recursive\ State\text{-}Action\ Policy
}
\]

核心区别：

1. 航空电子领域知识结构进入算法输入；
2. 文档适用性决定证据是否能进入 State；
3. Evidence Gap 不再是普通 missing information，而由领域证据状态和依赖关系产生；
4. Agent Action 被限定为航电知识获取动作；
5. RSI 学习的是经验证的 \(\Sigma_t\rightarrow\Sigma_{t+1}\) 状态迁移，而不是普通问答历史或动作成功次数；
6. 策略 Scope 与设备、模块、工况和 revision 绑定。

# 19. 当前专利主链候选

后续 Claim 1 不应保护 AERT / KEO / GAEU 三个名词本身，而应保护下述处理关系：

> 对航空电子装备知识任务建立包含任务相关证据槽位及槽位依赖关系的证据需求；对候选检索知识进行装备对象、功能模块、版本及工况适用性校验，并依据校验结果更新各证据槽位的状态；根据未满足、部分满足或冲突的证据状态确定当前证据缺口，并据此从领域知识获取动作中选择后续检索动作；在执行所述检索动作后验证证据状态迁移；记录经验证的任务上下文、迁移前证据状态、检索动作及迁移后证据状态，并根据历史验证状态迁移调整后续相似证据状态下的检索动作选择。

该主链是 V0.5 之后查新和权利要求设计的固定基准。

# 20. 后续 Stop Rule

后续专利检索不再因为发现某个局部模块已有类似做法就推倒重构。

只有出现以下情况才重新设计核心：

1. **单篇现有技术基本覆盖上述完整主链；**
2. **最接近现有技术仅需结合一个明确、常规且具有直接技术启示的手段，即可自然得到上述主链。**

若仅发现 missing evidence、metadata filter、version gate、feedback memory、evidence gain、Agent tool selection 等局部技术分别存在于不同文献中，但没有形成上述航空电子证据状态迁移闭环，则只用于调整权利要求边界和创造性论证，不再触发无限重构。
